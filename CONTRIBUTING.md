# Правила участия в проекте

## Основная ветка

Основная ветка проекта — `master`. Если в обсуждении она случайно названа `main`, под этим подразумевается `master`, пока репозиторий явно не переименован.

Ветка `develop` не используется.

## Начало новой задачи

- Если работа начинается из чистой `master`, создайте новую ветку задачи.
- Если текущая ветка уже является рабочей веткой, продолжайте работу в ней и не создавайте дополнительную ветку автоматически.
- Если в `master` есть незакоммиченные изменения, агент должен остановиться и спросить пользователя. С разрешения пользователя новая ветка создаётся вместе с этими изменениями. Без разрешения пользователь сначала самостоятельно коммитит или убирает изменения.
- Агент не должен самостоятельно коммитить, отправлять, сливать, перебазировать или помечать тегами изменения.

### Номер задачи

Каждая новая ветка соответствует новой задаче. Номер определяется автоматически:

1. Просмотрите существующие локальные и доступные remote-tracking ветки.
2. Найдите наибольший номер в именах, соответствующих принятому формату.
3. Используйте следующий номер. Если подходящих веток нет, начните с `1`.

## Имена веток

Формат:

```text
<type>-<task-number>/<short-kebab-description>
```

Примеры:

```text
feature-2/note-editor
fix-3/task-sorting
chore-4/agent-settings
```

Допустимые типы:

| Тип | Когда используется |
| --- | --- |
| `feature` | Добавление новой пользовательской возможности или существенное расширение существующей |
| `fix` | Исправление дефекта или неправильного поведения |
| `refactor` | Изменение внутренней структуры без изменения ожидаемого поведения |
| `test` | Добавление или исправление только тестов без изменения production-кода |
| `docs` | Изменение только документации |
| `chore` | Настройка сборки, зависимостей, инструментов, CI или агентской конфигурации |

Тесты и документация, являющиеся частью новой фичи, не меняют тип задачи: они выполняются в её `feature`-ветке.

## Коммиты

Коммиты создаёт пользователь после проверки изменений агента.

Формат сообщения:

```text
<type>-<task-number>: <past-tense message in English>
```

Примеры:

```text
feature-2: added note editor
feature-2: covered note saving scenarios
fix-3: corrected task sorting
docs-4: documented contribution workflow
```

- Используйте английский язык и прошедшее время.
- Делайте небольшие осмысленные коммиты.
- Используйте номер текущей задачи.
- Тип коммита должен соответствовать типу ветки. `test` используется только для отдельной задачи, изменяющей исключительно тесты.
- Не используйте временные сообщения вроде `wip`, `changes` или `fix stuff`.

## Проверка перед завершением задачи

После завершения вертикального среза необходимо:

1. Запустить все применимые локальные unit-тесты проекта.
2. Запустить Robolectric-тесты только после явного разрешения пользователя.
3. Собрать debug-вариант приложения командой `./gradlew :app:assembleDebug` или `./gradlew.bat :app:assembleDebug` в Windows.
4. Исправить ошибки, относящиеся к текущей задаче, и повторить проверки.

Lint не входит в обязательную проверку и запускается только по прямому указанию пользователя. Screenshot-тесты, инструментальные тесты и эмулятор по умолчанию не используются.

## Слияние

- Рабочая ветка сливается в `master` обычным merge с merge commit.
- Squash и rebase перед слиянием не используются: отдельные коммиты задачи сохраняются.
- После успешного слияния рабочую ветку можно удалить.
